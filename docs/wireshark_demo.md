# Wireshark Demonstration Procedure (BCS502 — Transport Layer evidence)

This file is the capture procedure and explanation script for the demonstration.
The actual `.pcapng` must be recorded on the laptops — see `test_results.md` for
what has been captured so far (a sandbox cannot produce the laptop capture).

## 1. Capture setup

1. Connect the Host and both Viewers to the same Wi-Fi network / phone hotspot.
2. Install [Wireshark](https://www.wireshark.org/) on the Host (or a Viewer).
3. Start Wireshark and double-click the active **Wi-Fi adapter**.
4. Optional capture filter (limits capture size on a busy network):

   ```text
   tcp port 5000
   ```

5. Start the capture **before** the first Viewer connects.

## 2. Demonstration sequence (section 19.2 of the architecture)

| Step | What to show | Filter / where | What it proves |
|---|---|---|---|
| 1 | SYN, SYN-ACK, ACK | `tcp.flags.syn == 1` | TCP three-way handshake performed by the OS |
| 2 | IPv4 addresses and port 5000 | `tcp.port == 5000` | IP addressing; ports identify the processes |
| 3 | Sequence and acknowledgement numbers, flags, window, checksum | middle pane of any segment | TCP header fields the OS maintains |
| 4 | Data in both directions | `tcp.port == 5000 && tcp.len > 0` | Host → Viewer JPEG frames (type-2) and JSON; Viewer → Host JOIN/input JSON |
| 5 | FIN/ACK exchange on disconnect | `tcp.flags.fin == 1` | Graceful connection termination |

Display filter for the whole demo:

```text
tcp.port == 5000
```

Optional analysis filters — **use only if the event actually occurs** in your
capture; a healthy LAN may show none of them, and that is a normal result:

```text
tcp.analysis.retransmission
tcp.analysis.duplicate_ack
tcp.analysis.window_update
tcp.analysis.zero_window
tcp.checksum.status
```

## 3. Points to make while presenting

- The **5-byte application header** (type + length) is ours; every other reliable
  behaviour in the capture — handshake, sequence/acknowledgement numbers,
  retransmissions, receive windows, congestion control — is the **operating
  system's TCP**, not application code. The project deliberately does not
  reimplement any of it.
- TCP acknowledgements are generated by the TCP stack; they are not the
  application's `CONTROL_GRANTED` or `STATUS` JSON messages.
- The congestion window (`cwnd`) is internal sender state and is not a field in
  every segment header; do not claim the packet view shows it directly.
- The session code is visible in the capture (follow the TCP stream of a JOIN:
  right-click a Viewer→Host packet → *Follow → TCP Stream*). This is exactly why
  the code is a convenience gate, not real security — the demonstration says so
  out loud.
- A checksum warning in a local capture may be caused by adapter checksum
  offloading, not by actual corruption on the network.
